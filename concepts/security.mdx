## Authentication

All API requests require authentication via API key or JWT token. See [Authentication](/authentication) for details.

- **API keys** — for server-to-server integrations
- **JWT tokens** — for user sessions and dashboard access
- Tokens expire after **8 hours**
- API keys can be rotated at any time from the [dashboard](https://app.wede.pt/dashboard/settings)

## Transport Security

All communication with the Wede API is encrypted over HTTPS (TLS 1.2+). Unencrypted HTTP requests are rejected.

## Role-Based Access Control

Every user has a role that defines what they can see and do:

| Role | Access Level |
|------|-------------|
| `company_admin` | Full tenant access including billing and user management |
| `company_tech` | Technical access — API, webhooks, zones, parsers |
| `operational_supervisor` | Operational access — events, zones, dispatch, teams |
| `field_operator` | Field access — events and zone status only |
| `corporate_client` | Read-only access to reports and dashboards |
| `api_user` | Programmatic API access only, no dashboard |
| `country_admin` | Multi-tenant access for assigned countries |

## Audit Trail

Every operation performed in Wede is logged in an immutable audit trail:

- User identity and role
- Action performed
- Resource affected
- Timestamp and IP address
- Request ID for traceability

Audit logs are available in the [dashboard](https://app.wede.pt/dashboard/audit) and via the API.

## Data Privacy

- Event payloads are transported by Wede but not inspected or stored beyond delivery
- All data is processed within EU infrastructure (GCP europe-west1)
- Data residency is configurable per country and per zone
- GDPR-compliant data handling for EU operations

## API Key Security

<Warning>
  Never expose your API key in client-side code, public repositories, or logs.
</Warning>

Best practices:

- Store API keys in environment variables or a secrets manager
- Use separate API keys per integration or environment
- Rotate keys regularly via the dashboard
- Revoke compromised keys immediately

## Idempotency

All event submissions require an `idempotency_key`. This prevents duplicate processing if a request is retried due to network failure.

Choose idempotency keys that are unique per logical event:

```bash
"idempotency_key": "dispatch-2026-05-19-amb07-001"
```

## Compliance

Wede is designed for regulated industries:

- **Healthcare** — designed for HIPAA-compatible deployments
- **Banking** — PCI-DSS compatible transport layer
- **Government** — configurable data residency per jurisdiction
- **Audit** — immutable logs with full traceability
